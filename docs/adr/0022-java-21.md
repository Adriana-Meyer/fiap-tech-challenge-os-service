# ADR 0022: Java 21 nos quatro serviços e na Lambda

**Status**: Aceito
**Data**: 2026-11-15

## Contexto

Os quatro serviços e a Lambda de autenticação estavam no Java 17. O scanner do SonarQube Cloud, que analisa os serviços no CI, passou a exigir Java 21 ou superior para rodar: com o Java 17 o passo de análise falhava ao iniciar. Havia duas saídas: rodar só o scanner com um JDK 21 e manter o resto no 17, ou migrar tudo.

## Decisão

Migrar **tudo** para o Java 21 (LTS), antes da primeira validação na AWS:

- `java.version` de cada serviço no `pom.xml`, e `maven.compiler.source`/`target` da Lambda.
- Imagens Docker: `maven:3.9-eclipse-temurin-21` no build e `eclipse-temurin:21-jre` no runtime ([ADR 0004](0004-docker-multistage-build.md)).
- Workflows: `actions/setup-java` na versão 21 (build, testes, análise do Sonar e build da Lambda).
- Lambda: runtime `java21` no Terraform ([ADR 0011](0011-java-lambda.md)).

Spring Boot 3.2.5 suporta do Java 17 ao 21, assim como as demais dependências em uso (JaCoCo 0.8.11, ArchUnit 1.2.1, Testcontainers, Cucumber e o agente do New Relic 8.15). Nenhuma mudança de código foi necessária.

## Consequências

- **Uma versão só em todo o sistema**, a mais recente com suporte de longo prazo, e o scanner do Sonar roda no mesmo JDK do build.
- É uma **mudança de runtime**: o dimensionamento de CPU e memória (ResourceQuota, requests e limits) foi validado com o Java 17. O comportamento esperado é parecido, mas só a validação no cluster confirma.
- O ambiente local passa a precisar do JDK 21 para rodar o Maven e o IDE.
- Voltar ao Java 17 é reverter as quatro mudanças acima, sem impacto em dados.
- Validado localmente com `mvn verify` nos quatro serviços e na Lambda e com o ambiente `e2e/`; falta a validação no cluster.
